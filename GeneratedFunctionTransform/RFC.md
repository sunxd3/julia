# RFC: `Core.GeneratedFunctionTransform`, a generator whose body is a compiled `CodeInstance`

## 1. Summary

`Core.GeneratedFunctionTransform(transform, gen)` is a second kind of generator for `@generated` methods. Instead of running user code that returns an expression, it infers and compiles the call selected by the argument types with a caller-supplied `Compiler.AbstractInterpreter`, and returns a one-line body that `invoke`s the resulting `CodeInstance`. That instance stays on the real `MethodInstance`, keeps its edges, and is invalidated and regenerated by the ordinary world-age machinery.

It is best understood as the less opaque alternative to `Core.OpaqueClosure` for getting tool-compiled code into an ordinary call site: an opaque closure freezes the world and discards identity, this keeps both. In the terms Nash used on julia#58014, where an opaque closure is a "fixed world hidden edge" and a `@cfunction` a "dynamic world hidden edge", this is a world-clocked, visible edge.

## 2. Motivation

Contextual-dispatch layers, AD systems, and GPU compilers each own an `AbstractInterpreter` (overlay method table, custom lattice, program transform) and want `overdub(f, x)` to run `f(x)` compiled through it. Today there are two routes, and each severs the link between "code the tool compiled" and "the compiler's bookkeeping about validity and identity".

**Route 1: opaque closure.** Run the interpreter by hand to get `IRCode`, wrap it with `Core.OpaqueClosure(ir)`. What is lost:

- The world stops. `oc.world` is stamped at creation (`src/opaque_closure.c:135`); when `f` or anything under it is redefined, nothing tells the tool. Mooncake #1209 and #1218 are what this looks like in practice: a rule whose types were predicted in one world and whose closure was built in a later one drifts apart.
- Identity and edges are dead. The body lives in a throwaway Method outside every table; its instance is created with `min_world == max_world == world` and any edges it carries are stored but never registered as backedges (`src/opaque_closure.c:171`), so nothing can ever cap it.
- Every call across the type boundary of a closure built from IR has `Effects()` (`Compiler/src/abstractinterpretation.jl:3145`), the declared return type only, no argument specialization, and an indirect call through a loaded `specptr`.
- Caching is per creation site, not per specialization.
- The declared return type is a contract only on the opaque path. `return_type` on a closure answers from the declared `R` alone (julia#62101), a narrower inferred type is not IPO-safe (Keno, same thread), and when creation and call are inlined together the declaration is not enforced at all: on the in-tree build `@opaque Tuple{Int}->Int (x)->x+1.5` throws `TypeError` when called opaquely and returns 2.5 when inlined.
- Instances cannot live in package images. A closure reached from precompiled code segfaults on load (julia#55073, julia#62180), which Nash describes as unsound by design (julia#62183), and a generated function that returns one is refused outright during precompilation (`src/method.c:840`; Nash states the rule on Mooncake PR #593).
- Stack traces show nothing about where the closure came from. The attempts to give closures a real `MethodInstance` for backtraces (julia#41391, julia#46168) were abandoned.
- Tools end up maintaining a hand-driven copy of the optimizer pipeline on synthetic IR. Mooncake's `optimise_ir!` fabricates a top-level `MethodInstance`, runs `ir_abstract_constant_propagation`, `ssa_inlining_pass!`, `sroa_pass!` and `adce_pass!` manually, then freezes the result into a closure. Every rule-to-rule call is a boundary with all the costs above. Its per-(world, signature) `oc_cache` (`Mooncake.jl/src/interpreter/abstract_interpretation.jl:13`), its imposed return type (`Mooncake.jl/src/utils.jl:444`), MistyClosures' `replace_captures`, and the habit of keeping the IR next to the closure, are hand-built substitutes for a `CodeInstance` chain on the `MethodInstance`.

**Route 2: classic `@generated` with pasted IR.** Run inference inside the generator and return the inferred body as an AST. The native compiler then re-infers a body it did not produce, edges into the tool's world are gone, and the inliner may swap the tool's `CodeInstance` for the native one it holds for the same `MethodInstance`. The `OwnerSwapInterp` test (`Compiler/test/AbstractInterpreter.jl:756`) is the concrete failure: the native `owner_swap_target(2)` is 30, the overlaid one is 10, and before the fix in §5 a wrapper calling `invoke(f, ci, x)` returned 30. Mooncake PR #900 tried this route for real, returning a type-erased dual `CodeInfo` for the native compiler to re-infer; barriers were erased and boxed variables crashed.

The proposal removes the severed link. The tool's compiled result becomes a first-class `CodeInstance` that the rest of the compiler can see, trust, invalidate, and reuse. The primitive it builds on, `invoke(f, ::CodeInstance, args...)` (julia#56660, 1.12), was added as the way for external compilers to hand code back. Its one known user is Mason Protter's experimental Differ.jl (August 2026, Julia 1.13 only), which hand-rolls exactly this proposal: a `@generated` `frule!!`/`rrule!!` builds a `ContextualInterpreter` at the generator's world, runs `typeinf_ext_toplevel(..., SOURCE_MODE_ABI)` on a carrier method whose body the interpreter swaps in, and returns `invoke(carrier, ci, args...)`, with the transform's edges folded into the instance (`DifferForwards/src/forward_interp.jl:1970`). Its README gives the motivation: code generation "happens at compile-time inside a `@generated function`", so "the derivative code IS a normal CodeInstance, inlined and optimized exactly like anything else Julia compiles", and it replaces Mooncake's "two `OpaqueClosure`s sharing captured state" with two ordinary instances and an explicit tape value. The route is otherwise unused, which is why two ownership bugs on it (§5.1, §5.3) had gone unnoticed. Differ's own list of pain points is a specification for what a built-in mechanism must handle: generators see a `typemax` world sentinel and dispatch pinned to `primary_world` (§4.1 here), re-entrant `typeinf_ext_toplevel` from inside a generator is fragile (its issue #84), and recursion across generator boundaries needs cycle guards because each boundary gets a fresh interpreter (§4.2 here).

## 3. Design

### 3.1 Three decisions

**Decision 1. The artifact is a `CodeInstance` on the real `MethodInstance`.** `generate_transformed_body` (`Compiler/src/generators.jl:69`) looks the transformed signature up with `findsup` on the interpreter's own `method_table`, then calls `typeinf_ext_toplevel(interp, mi, SOURCE_MODE_ABI)`. The result hangs on `target(::Int)`'s cache chain with `owner = cache_owner(interp)`, next to the native instance, compiled through the interpreter's `codegen_cache`, with a proper world range, forward edges, and an `invoke` pointer. This is also where core developers have pointed for opaque closures themselves: Nash closed julia#55034 with "fix OpaqueClosure instead (to hold a CodeInstance, like invoke)", and julia#57996 asks for the same thing so that codegen never has to call inference.

```
MethodInstance target(::Int64)
  ├─ cache ──► CodeInstance owner=nothing   [native compiler]
  │              └─ next ──► CodeInstance owner=MyInterp  [the tool]  ◄── stub invokes this
  └─ backedges: (Tuple{typeof(target),Int64}, stub CI), stub CI
```

**Decision 2. The generated body is `invoke(f, ci, args...)`.** The native compiler never sees the transformed IR. `abstract_invoke` (`Compiler/src/abstractinterpretation.jl:2549`) already knows how to handle a constant `CodeInstance`: it checks the ABI signature, takes `rettype`, `exctype` and `ipo_purity_bits` at face value, narrows the caller's world range to the instance's, and records `InvokeCICallInfo`. `handle_invoke_call!` (`Compiler/src/ssair/inlining.jl:1211`) lowers that to `Expr(:invoke, ci, f, args...)`, `emit_invoke` (`src/codegen.cpp:6149`) emits a direct call to the instance's symbol, and `jl_f_invoke` handles the interpreted fallback. No new concept enters the native compiler.

**Decision 3. The inner instance is the stub's first edge.** `Compiler/src/generators.jl:115` sets `src.edges = svec(ci, lowering edges...)`, `src.min_world = max(ci.min_world, first(lookup_worlds))` and `src.max_world = min(ci.max_world, last(lookup_worlds))`. The `InferenceState` constructor (`Compiler/src/inferencestate.jl:446`) narrows the outer frame to that range, `compute_edges!` appends the edges, and `store_backedges` turns the instance into a backedge on `target(::Int)`. Redefining `target` caps the stub and its callers through `invalidate_code_instance` (`src/gf.c:2425`), and the runtime reruns the generator on the next call. Appendix A shows this happening with real world numbers.

### 3.2 Protocol

```julia
struct GeneratedFunctionTransform
    transform  # (argtypes::Type{<:Tuple}) -> Type{<:Tuple}
    gen        # (world::UInt) -> Compiler.AbstractInterpreter
end
```

The runtime calls `(g::GeneratedFunctionTransform)(world, source::Method, argtypes...)` exactly as for any generator (`jl_call_staged`, `src/method.c:719`). The generator:

1. reassembles the specialization signature from the runtime's layout (static parameters first, trailing varargs packed) and drops the generated function itself (`transform_signature`, `generators.jl:17`);
2. computes `lookup = transform(argsig)`; `transform` must return a tuple type with the same number and order of arguments, since the generated method forwards its own arguments positionally;
3. constructs `interp = gen(world)` and requires `get_inference_world(interp) == world` and `cache_owner(interp) !== nothing`;
4. `findsup(lookup, method_table(interp))`, honouring overlay tables and returning the lookup's valid world range;
5. refuses if the match is the specialization being generated (§4.2);
6. `typeinf_ext_toplevel(interp, mi, SOURCE_MODE_ABI)`;
7. builds the `invoke` stub with `GeneratedFunctionStub(identity, ...)` as a lowering helper, spreading varargs back out with `getfield`, and sets edges and world range.

If the interpreter belongs to a `Compiler` loaded as a package rather than the one in the system image, the entry point delegates to that module's `generate_transformed_body` (`generators.jl:30`, `:64`), because the runtime dispatches generators through `Core` and only the sysimage compiler's method is reachable.

## 4. Semantics that need to be explicit

### 4.1 Two worlds The runtime pins the task world to the generated method's `primary_world` while the generator runs (`src/method.c:807`), and `invoke_in_world` is a no-op inside that callback. So `transform` and `gen` are fixed by the definition of the generated method, get no edges, and redefining them affects only generated methods defined afterwards (tested at `Compiler/test/AbstractInterpreter.jl:814`). Only the lookup and the inner inference use the requesting `world`, explicitly. This resolves the open question in the original sketch about which world to recover: there are two, and they are different on purpose.

### 4.2 Recursion Three cases, of which only the first two were anticipated by the original sketch.

*The generator's own lookup.* `typeinf_ext_toplevel` on the inner `MethodInstance` bypasses `get_staged`, so inferring the looked-up method does not re-run the same generator for the same request. *`transform` selecting the specialization being generated* is refused outright.

*Recursion through the generated method.* A transformed body reaches the generated method for another callee, whose transformed body reaches the first: `ping(n) = overdub(pong, n-1)` with `pong(n) = overdub(ping, n-1)`, or simply any recursive callee compiled Mooncake-style, where every call in a transformed body goes through `overdub`. Each level starts a fresh top-level inference with a fresh interpreter and no parent frame, so the cycle detection inference applies within one frame graph never sees the level above; the runtime's inference engine (`src/engine.c`) detects a thread waiting on itself but treats same-thread re-entry as "proceed". Before the fix this recursed until the stack overflowed (880 generator runs and two stack-overflow warnings on the in-tree build), after which `get_staged` swallowed the error and the result happened to be right. The generator now keeps a per-task stack of the specializations being generated (`generating_stack`, `generators.jl`) and refuses a request already on it. That plugs into §4.4: the refused call site has no body to infer, so it is compiled as `Expr(:invoke, mi, ...)` of the generated method's `MethodInstance` with return type `Any` (verified: the dispatch is still resolved statically, only the code lookup moves to run time); at run time nothing is in progress, the body is already cached from the outer level, and the transform still applies. The cost is one code lookup and an untyped result per cycle edge. This is the same shape as Mooncake's `LazyDerivedRule` and Differ's in-progress guard, both hand-built for the same loop. The proper fix is the original sketch's future-work item: have the outer inference handle this generator kind inside `typeinf_edge`, so the inner inference joins the same frame graph and the ordinary cycle detection resolves it.

*Recursion inside a transformed body* (a callee calling itself) never reaches the generator; it is an ordinary inference cycle within the inner interpreter (tested with a factorial).

The artifact's identity is the pair (`MethodInstance`, owner). Rerunning the generator in the same world hits the interpreter's cache and yields the same instance, which is what makes the body safe to store in a package image. A `PartialOpaque` by contrast pins a `Method` by identity, which is why generated functions that return one are refused during precompilation (`src/method.c:840`).

### 4.3 Concrete argument types only `may_invoke_generator` (`base/runtime_internals.jl:1844`) is unchanged: for a generator that is not a `GeneratedFunctionStub` it only fires on dispatch tuples. Callers with abstract argument types infer `Any` through the generated method. This is a real cost relative to a typed opaque closure, whose declared `OpaqueClosure{ArgT, RetT}` still yields `RetT` in poorly inferred callers (enforced only on the opaque path, §2).

### 4.4 Failure The generator throws descriptive errors instead of returning `nothing`. Inside inference, `get_staged` (`Compiler/src/utilities.jl:88`) swallows the exception and the call infers `Any`; at runtime the error surfaces to the user (tested at `Compiler/test/AbstractInterpreter.jl:803`). Returning `nothing` would lose the reason in both paths.

### 4.5 Overlay method tables do not invalidate The runtime keeps method-table backedges only for the global table (`jl_method_table_add_backedge`, `src/gf.c:2715`). A method added to an overlay table after a body was generated does not invalidate it. This is a pre-existing limitation of `Compiler.OverlayMethodTable` and applies equally to the inner inference, but it bites this feature directly and must be documented.

### 4.6 Excluded from heuristics `method_for_inference_heuristics` (`Compiler/src/abstractinterpretation.jl:850`) skips this generator kind. Running a full inner inference is not a cheap probe, and its result carries no `method_for_inference_limit_heuristics`.

### 4.7 Dynamic calls inside the transformed body go to native dispatch A call the interpreter could not resolve statically is dispatched by the runtime through the global table in the caller's world, exactly as inside an opaque closure (julia#46220). Overdubbing dynamic calls stays the tool's job, as it is today.

### 4.8 The tool holds the IR In a running session the foreign instance's `inferred` field is cleared once the instance is activated, and its optimized IR lives only in the interpreter's `codegen_cache` (`Compiler/src/types.jl:609` for the native one). It is in `inferred` only during precompilation and after loading an image. So the tool owns the retention policy for its IR, and that cache grows with every specialization unless the tool bounds it, the same class of problem as Mooncake #1116.

## 5. Required changes outside the generator

**5.1 `compileable_specialization` must respect ownership** (`Compiler/src/ssair/inlining.jl:781`). The optimizer prefers to replace a given `CodeInstance` with whatever the current interpreter's code cache holds for the same `MethodInstance`, to widen to a compileable signature. With two owners on one chain that silently swaps the tool's code for native code. The fix keeps the direct edge whenever `code.owner !== cache_owner(state.interp)`. This is also what makes user-level `invoke(f, ci, args...)` honest for any foreign-owned instance, independent of generators.

**5.2 The C edge decoder in `jl_code_for_staged`** (`src/method.c:875`) converts a `CachedGenerator`'s forward edges into backedges. It only understood `MethodInstance`, `Binding`, and `(MethodTable, sig)` entries, and had the pair order inverted relative to `ForwardToBackedgeIterator` (`Compiler/src/typeinfer.jl:822`). It now mirrors that iterator case for case: lookup groups (`nmatches, atype, matches...`), `Method` entries (ignored), `CodeInstance` entries, and `(invokesig, callee)` pairs. `GeneratedFunctionTransform` is not a `CachedGenerator` and does not take this path, but any cached generator that records a `CodeInstance` edge needs it (`test/staged.jl:431`). This is separable and would make a clean first commit.

**5.3 Package images must emit foreign-owned `:invoke` targets** (`Compiler/src/typeinfer.jl:2132`, `compile!`). The image compilation driver looked a `:invoke` edge up only in the native interpreter's `codegen_cache`; a foreign-owned `CodeInstance` is never there, so the driver re-inferred its `MethodInstance` natively and never emitted the foreign code, and `aot_link_output` (`src/aotcompile.cpp:908`) resolved the dangling call with a thunk that re-dispatches by `MethodInstance`. Loaded from the image, `caller(2)` from Appendix A returned the native 31 instead of 11, silently. The driver now emits a foreign-owned instance from the optimized IR that `inferred` holds during precompilation (§4.8; the serializer keeps it for foreign owners, `src/staticdata_utils.c:148`) whenever `callee.owner !== cache_owner(interp)`. Like §5.1, this is a fix for user-level `invoke(f, ci, args...)` that this feature merely exposes. The link-time fallback itself still re-dispatches by `MethodInstance` for an uncompiled foreign instance and should become an error (§8.3).

**5.4 Derived bodies.** The generator infers whatever method the lookup finds; it does not let the interpreter supply a body of its own. That is enough for "the same call, compiled by my interpreter", and it composes with an ordinary `@generated` method for the derived case: the tool defines `evaluate(::Val{tag}, x)` (or `rrule!!(f, x)`) as a generated method that pastes its derived IR, and the transform looks that method up and infers it under the tool's interpreter. This is Route 2 without its failure, since the re-inference happens in the tool's domain, and it is what the runtime-expression demo below does. Differ instead swaps the body in `finishinfer!` on a carrier method; the RFC does not add a hook for that, and should say so.

**Deliberate non-changes:** `may_invoke_generator`; `jl_type_infer` in `src/gf.c` (the original's step 7, see §7).

## 6. What crosses the boundary, and what does not

Facts about the transformed body that now reach the native caller, versus an opaque closure:

| Fact | `GeneratedFunctionTransform` | `OpaqueClosure` |
|---|---|---|
| Return type | inferred per concrete signature | declared `RetT`, enforced only opaquely |
| Effects | from `ipo_purity_bits` | `Effects()` (unknown) |
| Constant result | folded at codegen (`src/codegen.cpp:6153`) | call |
| Call | direct, known symbol | indirect through `specptr` |
| World range | on the world clock, capped by backedges | frozen |
| Caching | per specialization, shared by all call sites | per creation site |
| Callee-to-callee inside the transform | one inference domain | a boundary per closure |
| Stack frames | real: `error <- leaf <- target <- overdub <- caller` | none for the closure's origin |
| Package image | ordinary instance, serialized with its owner | segfault (julia#55073) |

Deliberately still opaque: the transformed body is never inlined into native code, because it was produced under a different method table or lattice. Unlike the closure case, where cross-world inlining is unsound by construction, here it is a policy that an owner could relax later (§8).

## 7. Departures from the original sketch

- Constructor takes both fields, `(transform, gen)`, as the field list requires.
- The callable is `(g)(world, source::Method, argtypes...)`, the real runtime protocol, not `(world, argtypes...)`.
- Failures throw instead of returning `nothing` (§4.4).
- Step 7 of the original, having `jl_type_infer` construct `owner(world)` in C and pass it down, is not implemented. The Julia-side path did not need it. The original's "future work" idea, letting the outer inference recognize this generator kind and retrieve the inner interpreter directly instead of going through `jl_code_for_staged`, remains open and would build on that hook.
- Two supporting fixes (§5) were not anticipated.

## 8. Open questions

1. **Inference-time constant folding.** `abstract_invoke` returns the widened `rettype` even when the instance has `rettype_const`; codegen folds it, inference does not. Returning a `Const` is a small change that would let native inference fold through the boundary.
2. **Opt-in inlining.** Should an owner be able to declare its code native-compatible so the native inliner may pull the body in? The ownership check in §5.1 is where such a policy would live.
3. **Package images.** Now tested (§5.3, `test/precompile.jl`): the generated body, its foreign-owned instance with native code, and a native caller all round-trip through a package image, the body is not regenerated on load, and redefinition after load still invalidates and regenerates. Edge verification lives in `Compiler/src/reinfer.jl` (`verify_method`). Remaining: the `aot_link_output` fallback for an uncompiled foreign-owned instance should error like `src/builtins.c:1948` instead of re-dispatching by `MethodInstance`. This is the concrete advantage over an opaque closure, whose instances cannot survive a package image at all (julia#55073, julia#62180). `--trim` also works: the Appendix A program built with JuliaC `--trim=safe` into a standalone executable prints 11, with no trim-verifier warnings and a binary the size of the `Hello` example (1.7 MB, so no compiler was bundled). julia#57996 wants dispatch resolved before codegen, and the stub does exactly that. This is not yet a test under `test/trim/`.
4. **Abstract callers** (§4.3). Is inferring `Any` acceptable, or should the generated method be allowed to fall back to a declared return type?
5. **Naming.** Given that users will reach for this as the alternative to `OpaqueClosure`, is `GeneratedFunctionTransform` the right name?
6. **Adjacent proposals.** `TypedCallable` / `InvokeLatestCallable` (julia#59774, julia#62245, julia#62559) are a latest-world ABI bridge for callables known only at runtime; this is a world-clocked body for a compile-time transform. Same direction, on the clock rather than frozen, different niche. Keno's draft `await` mechanism (julia#58532) replaces `:new_opaque_closure` for AD residuals and may overlap with the AD use case here; it has not been compared.

## 8b. A second use: runtime expressions without `eval`

Hash a runtime expression into a type tag, paste it in one ordinary generated method `evaluate(::Val{tag}, x)`, and reach it through the transform. On the in-tree build: the world counter does not move, callers infer `Float64` rather than `Any`, the generator runs once per (tag, argument types), redefining a helper the expression uses regenerates it, a new expression costs one more generator run, and an error inside it shows real frames through `evaluate` and the generated method. Relative to RuntimeGeneratedFunctions, which already avoids `eval` this way, the transform adds compilation by the tool's interpreter (an overlay applies inside the expression), a result that stays an ordinary call, and an instance with edges that survives a package image. Constraints: the expression must be reachable from a type, so a call site that sees many expressions dispatches dynamically, and the tag must be a content hash because the registry lookup is a hidden edge.

## 9. Tests

Existing, and what each proves:

- `Compiler/test/AbstractInterpreter.jl:756` `OwnerSwapInterp`: `invoke(f, ci, x)` keeps targeting a foreign-owned instance once the native cache is populated (§5.1).
- `:780` `gft_overdub`: the end-to-end path, plus redefinition of the target regenerating the body (`gft_caller(2)` goes from 11 to 101).
- `:803`: the error surfaces at runtime for a non-matching signature.
- `:814` `gft_overdub2/3`: `transform` is fixed by the generated method's definition, and a widening `transform` selects the wider method.
- `:833` `gft_overdub4`: anonymous arguments work.
- `test/staged.jl:431` `GeneratorCIEdge`: a `CachedGenerator` recording a `CodeInstance` edge gets a correct backedge (§5.2).
- `test/precompile.jl` "GeneratedFunctionTransform invoke edge": a package whose caller of the generated method is precompiled loads with the foreign-owned instance's native code in the image, answers through the overlay without regenerating, and regenerates after a redefinition in the loading session (§5.3).

Gaps: an interpreter from a separately loaded `Compiler` package; `--trim` (run by hand, §8.3, not yet a `test/trim/` project).

| Event | World |

After the first call:

```
target(::Int64)   CI owner=MyInterp  worlds=[42917, ∞]  edges: leaf CI (foreign), * CI (foreign)
                  backedges: Tuple{typeof(target),Int64}, stub CI ; stub CI
overdub(target,Int64)  CI owner=nothing  worlds=[42919, ∞]
                  edges: Tuple{typeof(target),Int64} | target CI (foreign) | target CI (foreign)
caller(::Int64)   CI owner=nothing  worlds=[42925, ∞]  edges: overdub CI | + CI
```

Invalidation log on redefinition, in order: stub at depth 1, `caller` at depth 2, stub again at depth 1 (already capped, no recursion), then the method-level entries.

After redefinition and one more `caller(2)` = 101:

```
old target CI     owner=MyInterp  worlds=[42917, ∞]     (unreachable; never capped)
overdub  CIs      [42939, ∞]  then  [42919, 42938]      (new in front, capped behind)
caller   CIs      [42939, ∞]  then  [42925, 42938]
```

Notes. The inner instance's `min_world` (42917) predates `target` itself because a `CodeInstance` range reflects its callees, not its own method; the stub still starts at 42919 because §3.1 Decision 3 intersects with the lookup range. The doubled edge (pair from `InvokeCICallInfo`, bare from `src.edges`) is deduplicated by `store_backedges` per (item, signature) and is harmless.

# RFC: `Core.GeneratedFunctionTransform`, a generator whose body is a compiled `CodeInstance`

Anchors are `path:line` against `bf0b277ba0` ("Compiler: Do not re-infer a foreign-owned invoke target natively", the last of the six fix commits on master `55312b3c97`). Code added by the feature commit ("Compiler: Add Core.GeneratedFunctionTransform, an interpreter-backed generator") is cited by file and name; its line numbers are marked *(line not verified)*.

## 1. Summary

`Core.GeneratedFunctionTransform(gen)` is a second kind of generator for `@generated` methods. Instead of running user code that returns an expression, it infers and compiles the call formed by the generated method's own arguments with the `Compiler.AbstractInterpreter` returned by `gen(world)`, and returns a one-line body that `invoke`s the resulting `CodeInstance`. That instance stays on the real `MethodInstance`, keeps its edges, and is invalidated and regenerated by the ordinary world-age machinery.

It is best understood as the less opaque alternative to `Core.OpaqueClosure` for getting tool-compiled code into an ordinary call site: an opaque closure freezes the world and discards identity, this keeps both. In the terms Nash used on julia#58014, where an opaque closure is a "fixed world hidden edge" and a `@cfunction` a "dynamic world hidden edge", this is a world-clocked, visible edge.

The struct is also the hook for the intended end state (§8): the native compiler recognises this generator kind and infers through it with the inner interpreter, instead of treating it as an opaque generator. A plain generator function would work today but would give the compiler nothing to recognise.

## 2. Motivation

Contextual-dispatch layers, AD systems, and GPU compilers each own an `AbstractInterpreter` (overlay method table, custom lattice, program transform) and want `overdub(f, x)` to run `f(x)` compiled through it. Today there are two routes, and each severs the link between "code the tool compiled" and "the compiler's bookkeeping about validity and identity".

**Route 1: opaque closure.** Run the interpreter by hand to get `IRCode`, wrap it with `Core.OpaqueClosure(ir)`. What is lost:

- The world stops. `oc.world` is stamped at creation (`src/opaque_closure.c:135`); when `f` or anything under it is redefined, nothing tells the tool. Mooncake #1209 and #1218 are what this looks like in practice.
- Identity and edges are dead. The body lives in a throwaway Method outside every table; its instance has `min_world == max_world == world` and its edges are stored but never registered as backedges (`src/opaque_closure.c:171`).
- Every call across the type boundary of a closure built from IR has `Effects()` (`Compiler/src/abstractinterpretation.jl:3159`), the declared return type only, no argument specialization, and an indirect call through `specptr`.
- The declared return type is a contract only on the opaque path: `@opaque Tuple{Int}->Int (x)->x+1.5` throws `TypeError` when called opaquely and returns 2.5 when inlined (julia#62101 for the IPO side).
- Instances cannot live in package images (julia#55073, julia#62180, julia#62183), and a generated function returning one is refused during precompilation (`src/method.c:865`).
- Tools maintain a hand-driven copy of the optimizer pipeline on synthetic IR (Mooncake's `optimise_ir!`, its per-(world, signature) `oc_cache` at `Mooncake.jl/src/interpreter/abstract_interpretation.jl:13`, its imposed return type at `Mooncake.jl/src/utils.jl:444`); every rule-to-rule call is a closure boundary.

**Route 2: classic `@generated` with pasted IR.** The native compiler re-infers a body it did not produce, edges into the tool's world are gone, and on master the inliner swaps the tool's `CodeInstance` for the native one it holds for the same `MethodInstance` (fix (b), §5). Mooncake PR #900 tried this route; barriers were erased and boxed variables crashed.

The proposal removes the severed link. The tool's result becomes a first-class `CodeInstance` that the rest of the compiler can see, trust, invalidate, and reuse. The primitive it builds on, `invoke(f, ::CodeInstance, args...)` (julia#56660, 1.12), was added as the way for external compilers to hand code back. The only user we know of is Mason Protter's experimental Differ.jl (started July 2026, Julia 1.13 only, "made for fun" per its README), which hand-rolls this proposal: a `@generated` `frule!!`/`rrule!!` builds a `ContextualInterpreter` at the generator's world, runs `typeinf_ext_toplevel(..., SOURCE_MODE_ABI)` on a carrier method whose body the interpreter swaps in via `finishinfer!`/`optimize` overrides (`Contextual/src/Contextual.jl:198-236`), and returns `invoke(dualized_impl, cinst, dualargs...)` (`DifferForwards/src/forward_interp.jl:1970`; both checked at `e61b6b1`). Its README gives the motivation: code generation "happens at compile-time inside a `@generated function`"; a source comment in its reverse mode (`DifferReverse/src/reverse_interp.jl:18`) contrasts Mooncake's "two `OpaqueClosure`s sharing captured state" with "ordinary `CodeInstance`s" and an explicit tape. The route is otherwise unused, which is why the ownership bugs on it (§5) had gone unnoticed. Differ's pain points are a specification for what a built-in mechanism must handle: generators see a `typemax` world sentinel and dispatch pinned to `primary_world` (§4.1), re-entrant `typeinf_ext_toplevel` from inside a generator is fragile (its issue #84; fix (d)), and recursion across generator boundaries needs cycle guards (§4.2).

## 3. Design

### 3.1 Three decisions

**Decision 1. The artifact is a `CodeInstance` on the real `MethodInstance`.** The generator looks the call up with `findsup` on the interpreter's own `method_table`, then calls `typeinf_ext_toplevel(interp, mi, SOURCE_MODE_ABI)`. The result hangs on `target(::Int)`'s cache chain with `owner = cache_owner(interp)`, next to the native instance, compiled through the interpreter's `codegen_cache`, with a world range, forward edges, and an `invoke` pointer. This is where core developers have pointed for opaque closures themselves: Nash closed julia#55034 with "fix OpaqueClosure instead (to hold a CodeInstance, like invoke)", and julia#57996 asks for the same so that codegen never has to call inference.

```
MethodInstance target(::Int64)
  ├─ cache ──► CodeInstance owner=nothing   [native compiler]
  │              └─ next ──► CodeInstance owner=MyInterp  [the tool]  ◄── stub invokes this
  └─ backedges: (Tuple{typeof(target),Int64}, stub CI), stub CI
```

**Decision 2. The generated body is `invoke(f, ci, args...)`.** The native compiler never sees the transformed IR. `abstract_invoke` (`Compiler/src/abstractinterpretation.jl:2527`) already handles a constant `CodeInstance`: it checks the ABI signature, takes `rettype`, `exctype` and `ipo_purity_bits` at face value, narrows the caller's world range to the instance's, and records `InvokeCICallInfo`. `handle_invoke_call!` (`Compiler/src/ssair/inlining.jl:1203`) lowers that to `Expr(:invoke, ci, f, args...)`, codegen emits a direct call to the instance's symbol, and `jl_f_invoke` is the interpreted fallback. This choice was the first implementer's, not the original sketch's; §8 compares it with returning the transformed body directly.

**Decision 3. The inner instance is the stub's first edge.** The generator sets `src.edges = svec(ci, lowering edges...)`, `src.min_world = max(ci.min_world, first(lookup_worlds))` and `src.max_world = min(ci.max_world, last(lookup_worlds))` (end of `generate_transformed_body` in `Compiler/src/generators.jl`, *(line not verified)*). The `InferenceState` constructor (`Compiler/src/inferencestate.jl:446`) narrows the outer frame to that range and `store_backedges` turns the instance into a backedge on `target(::Int)`. Redefining `target` caps the stub and its callers through `invalidate_code_instance` (`src/gf.c:2424`), and the next call reruns the generator. Appendix A shows this with real world numbers.

### 3.2 Protocol

```julia
struct GeneratedFunctionTransform   # Core
    gen   # (world::UInt) -> Compiler.AbstractInterpreter
end
```

The runtime calls `(g::GeneratedFunctionTransform)(world, source::Method, args...)` exactly as for any generator (`jl_call_staged`, `src/method.c:719`). That call method lives in Base (`base/reflection.jl` *(line not verified)*, next to `invoke_interp_compiler` at `:328`, which already routes reflection to a package-loaded `Compiler` by walking supertypes to `AbstractInterpreter`). It

1. runs `interp = g.gen(world)`;
2. finds the interpreter's `Compiler` module (`interp_compiler`) by walking `supertype` to a type named `AbstractInterpreter` whose module owns that binding (`getglobal(mod, :AbstractInterpreter) === T.name.wrapper`); errors clearly if there is none, and errors naming the module if it lacks `generate_transformed_body` (an older `Compiler`);
3. calls that module's `generate_transformed_body(g, interp, world, source, args)`.

`Compiler` keeps only the implementation, which:

4. reassembles the specialization signature from the runtime's layout (static parameters first, trailing varargs packed) and drops the generated function itself (`transform_signature` in `generators.jl`), giving `lookup = Tuple{typeof(f), argtypes...}`;
5. requires `get_inference_world(interp) == world`, and throws an `ArgumentError` if `cache_owner(interp) === nothing` (§4.4);
6. `findsup(lookup, method_table(interp))`, honouring overlay tables and returning the lookup's valid world range;
7. `typeinf_ext_toplevel(interp, mi, SOURCE_MODE_ABI)`;
8. builds the stub with `GeneratedFunctionStub(identity, ...)` as a lowering helper (`base/expr.jl:1884`), spreading varargs back out with `getfield`, and sets edges and world range.

In Base the call method needs no guard against a package-loaded `Compiler` overwriting it, as the earlier `Compiler`-side definition did, since Base is never loaded twice (Appendix E).

**There is no `transform` field.** The stub forwards the generated method's own arguments positionally, so a signature-changing hook cannot redirect to another function or change arity: both fail at the `invoke` with `TypeError` (Appendix D). Its only remaining power was to pick a less specific method of the same function, which the interpreter's `method_table` already governs. The derived-body case the previous revision handled with it is expressed by passing the rule function as the first argument: `overdub(rrule!!, f, x)` looks up `rrule!!(f, x)` and compiles it under the tool's interpreter. If `rrule!!` is itself an ordinary `@generated` method pasting derived IR, that re-inference happens in the tool's domain, which is Route 2 without its failure. Differ instead swaps the body in `finishinfer!` on a carrier method; the RFC adds no hook for that.

## 4. Semantics that need to be explicit

### 4.1 Frozen and live worlds

`jl_call_staged` runs every generator with `ct->world_age = primary_world` of the generated method and `in_pure_callback` set (`src/method.c:831-832`). Inside, `invoke_in_world` and `invokelatest` are no-ops (`src/builtins.c:1052`, `:1068`) and `get_world_counter()` returns `typemax` (`src/gf.c:55`). Measured consequences (Appendix C):

- **Frozen:** `gen` and everything the interpreter *type* does through plain dispatch, including its `method_table` overload and any trait it consults, are fixed at the definition of the generated method. A `method_table` overload defined after the generated method is not seen (case A: 30, untransformed); a trait flipped afterwards is not seen (case C).
- **Live:** lookups that take an explicit world, `findsup` on the interpreter's `OverlayMethodTable(world, MT)` and the inner inference itself, use the requesting world. An overlay rule added after the generated method *is* seen (case B: 10).
- **The freeze poisons the owner's cache.** A result inferred under the frozen view is stored under the interpreter's owner with `max_world = ∞` and reused by every later user of that owner: a generated method defined *after* the overload still returns the stale 30 for the same target, and so does a direct latest-world `typeinf_ext_toplevel(MyInterp(), ...)` (case A). The root cause is general, not specific to this feature: an interpreter's own methods have no edges, so nothing records that the cached result depended on them.

Options considered. *Run this generator kind in the requesting world*: a one-line change, but results become stale and compile-order dependent, since the interpreter's methods still carry no edges (measured by the author; case D reproduces the same behaviour through `Core._call_in_world_total`: first answer 10, still 10 after the trait is flipped back, 30 for a fresh target in the same world). Rejected. *Nash's `typeinf_edge` integration* (§8) does not remove the pin: native inference runs in `jl_typeinf_world` (`src/gf.c:469`), so interpreter code would be frozen at the compiler's world instead.

Recommendation: keep the pin and document the split. Interpreter behaviour is frozen; rules that must track redefinition should be *methods looked up with an explicit world* (overlay tables, `findsup`), which get edges; and a tool whose interpreter behaviour can change within a session should put a version token in `cache_owner`, so a changed interpreter gets a fresh cache instead of the poisoned one. `Core._call_in_world_total` ignores `in_pure_callback` (`src/builtins.c:1078`) and is a loophole around the pin (question 8, §8).

### 4.2 Recursion

*The generator's own lookup.* `typeinf_ext_toplevel` on the inner `MethodInstance` bypasses `get_staged`, so inferring the looked-up method does not rerun the same generator. The lookup can never resolve to the specialization being generated: it is the generated method's arguments minus the generated function itself, so it is one argument shorter than that specialization's signature. Passing the generated function as its own first argument (`overdub(overdub, f, x)`) looks up `overdub(f, x)`, a different specialization, which is ordinary nested generation governed by the runtime bound below. The earlier design's up-front refusal of a same-specialization match existed only because `transform` could return an arbitrary signature; it is gone with the field.

*Recursion through the generated method.* `ping(n) = overdub(pong, n-1)` with `pong(n) = overdub(ping, n-1)`, or any recursive callee compiled Mooncake-style. Each level starts a fresh top-level inference with a fresh interpreter, so inference's cycle detection never sees the level above, and `jl_engine_reserve` hands a same-thread re-entry a placeholder (`src/engine.c:66`). On 1.13.0 this recurses to stack overflow (upstream bug 10). The guard is the runtime's (fix (d)): `jl_code_for_staged` keeps a per-thread stack of `MethodInstance`s being generated and refuses the *second* re-entry of the same one (`src/method.c:804`). Per-thread is exact because task switches are forbidden inside a generator (`src/task.c:680`). One re-entry is allowed because inference entered through `jl_type_infer` already bounds that level (`jl_engine_hasreserved`, `src/gf.c:443`), and refusing it regressed the `wrapper62338_gencache` test (`Compiler/test/inference.jl:70`). `get_staged` swallows the error (`Compiler/src/utilities.jl:88`), the refused call site is compiled as an `:invoke` of the generated method's `MethodInstance` with result `Any`, and at run time it finds the body finished by the outer level. Counts: ping/pong runs the generator 4 times (each specialization generated once, re-entered once), self-recursion 2 times. That is twice the runs of the earlier Julia-side per-task guard, which covered only this generator kind. The proper fix is the §8 integration, where the inner inference joins the outer frame graph.

*Recursion inside a transformed body* (a callee calling itself) never reaches the generator; it is an ordinary inference cycle within the inner interpreter.

The artifact's identity is the pair (`MethodInstance`, owner). Rerunning the generator in the same world hits the interpreter's cache and yields the same instance, which is what makes the body safe to store in a package image; a `PartialOpaque` pins a `Method` by identity, which is why generated functions returning one are refused during precompilation (`src/method.c:865`).

### 4.3 Concrete argument types only

`may_invoke_generator` (`base/runtime_internals.jl:1857`) is unchanged: for a generator that is not a `GeneratedFunctionStub` it fires only on dispatch tuples. Callers with abstract argument types infer `Any`, a real cost relative to a typed opaque closure.

### 4.4 Failure and `cache_owner`

The generator throws descriptive errors instead of returning `nothing`. Inside inference `get_staged` swallows the exception and the call infers `Any`; at run time the error surfaces to the user. `cache_owner(interp) === nothing` is an `ArgumentError`: the inner result would be written into the native cache as if the native compiler had produced it, poisoning unrelated native code (measured by the author).

### 4.5 Overlay method tables do not invalidate

The runtime keeps method-table backedges only for the global table (`jl_method_table_add_backedge`, `src/gf.c:2713`). A method *added* to an overlay table after a body was generated does not invalidate it; *replacing* an existing overlay method does, through `MethodInstance` backedges. Pre-existing limitation of `Compiler.OverlayMethodTable`, applies equally to the inner inference.

### 4.6 Excluded from heuristics

`method_for_inference_heuristics` (`Compiler/src/abstractinterpretation.jl:850`) skips this generator kind: a full inner inference is not a cheap probe.

### 4.7 Dynamic calls inside the transformed body go to native dispatch

A call the interpreter could not resolve statically is dispatched through the global table in the caller's world, as inside an opaque closure (julia#46220). Overdubbing dynamic calls stays the tool's job.

### 4.8 The tool holds the IR

In a running session the foreign instance's `inferred` is cleared once activated, and its IR lives only in the interpreter's `codegen_cache` (`Compiler/src/types.jl:609` for the native one); it is in `inferred` only during precompilation and after loading an image (`src/staticdata_utils.c:148`). The tool owns the retention policy, and the cache grows with every specialization unless the tool bounds it (cf. Mooncake #1116). A foreign instance that reaches a compile driver without source is skipped, and its call raises at run time instead of running native code (fix (f)).

### 4.9 Limitations

- **`--compile=min`.** The interpreted stub invokes a foreign instance that was never compiled and fails with "Failed to invoke or compile external codeinst". Reproduced for interpreters without a `codegen_cache` (e.g. `@newinterp` from `Compiler/test/newinterp.jl`) on both the branch build and the rebuilt tree (Appendix G); with a `codegen_cache` the same program returned the right answer on both.
- **Keyword arguments** are unsupported: the generated method is reached through the kwsorter ABI, whose leading arguments are keyword values rather than the callee, so the generator refuses any method with `nkw != 0` with "GeneratedFunctionTransform: keyword arguments are not supported (in …)" (`generate_transformed_body` in `Compiler/src/generators.jl`).
- **Overlay additions** do not invalidate (§4.5).
- **Trust.** `invoke(f, ci, ...)` believes the instance's `rettype` and effects. That is a pre-existing unsafe primitive (julia#56660); this feature makes it reachable more often, and anything the tool reads without recording an edge is invisible to invalidation.
- **`--trim`** was tested by hand only: once, on the pre-fix branch (2026-09-15), the Appendix A program built with JuliaC `--trim=safe` printed 11 with an empty build log. `verifytrim` cannot see an owner swap, so a clean verifier log is not evidence of correctness, and there is no `test/trim/` project.

## 5. Required changes outside the generator

Six fixes, each a separate commit preceding the feature commit, none caused by it. Numbers refer to `GeneratedFunctionTransform/upstream-bugs.md`.

**(a) "method: Fix the backedge decoder in jl_code_for_staged"** (`a1f89db502`; bug 1; `src/method.c:902`). The C copy of `ForwardToBackedgeIterator` (`Compiler/src/typeinfer.jl:824`) tested the pair order backwards and did not know `CodeInstance` or lookup-group entries; they fell into a branch that casts the second element to `MethodInstance` and writes through the wrong struct. Without it: segfault on released 1.12.7 and 1.13.0 for a `Core.CachedGenerator` recording such edges, and for any generator on the interpreted path (`src/interpreter.c:909`).

**(b) "inlining: Keep a foreign-owned CodeInstance as the invoke target"** (`b83ee11318`; bug 4; `compileable_specialization`, `Compiler/src/ssair/inlining.jl:813`). Since julia#60442 made `invoke(f, ci, ...)` a static `:invoke`, the inliner replaced the given instance with whatever the native cache held for the same `MethodInstance`. Without it the feature does not work at all: the transformed body is discarded whenever the target also has a native instance, the common case (`OwnerSwapInterp` test: 30 instead of 10). 1.13.0 has the same wrong answer by a different route, needing its own backport patch.

**(c) "inference: Do not infer invoke of a foreign CodeInstance as nothrow"** (`a674ac2f56`; bug 7; `abstract_invoke`, `Compiler/src/abstractinterpretation.jl:2558`). It compared `owner` to the type `Nothing`, so `invoke` of a foreign instance was inferred nothrow and a caller discarding the result had the call deleted, while the runtime would have thrown.

**(d) "method: Bound re-entrant generation of a MethodInstance"** (`e45303dd4a`; bug 10; `src/method.c:804`). §4.2. Without it, recursion through the generated method overflows the stack (1.12.7, 1.13.0).

**(e) "codegen: Never dispatch a foreign-owned CodeInstance by MethodInstance"** (`6ac267d373`; bugs 6, 9). The `tojlinvoke` trampoline and the `needsparams` arm of `emit_invoke` called `jl_invoke(mi)`, running the native body. New `jl_invoke_codeinst` (`src/gf.c:4674`, shared with `jl_f_invoke`) runs the instance itself or raises the `invoke` builtin's error (`src/codegen.cpp:6335`, `:7961`). Without it a precompiled or JIT-linked caller of a non-inlineable foreign instance silently returns the native result.

**(f) "Compiler: Do not re-infer a foreign-owned invoke target natively"** (`bf0b277ba0`; bugs 5, 8, 9). `add_codeinsts_to_jit!` and the package-image `compile!` re-inferred a source-less foreign `:invoke` target under the native owner and inserted it into the native cache (asserting on the owner check). Now they emit it from its own source, else skip it and leave it to (e)'s trampoline; under `--trim`, where there is no runtime fallback, it is reported like the trim verifier reports: a hard failure under `--trim=safe`, a warning under `--trim=unsafe-warn`, skipped under `--trim=unsafe` (`is_foreign_owned`, `Compiler/src/typeinfer.jl:2031`; `:2190`). Without it a loaded image answers with the native callee (31 instead of 11), or precompilation dies on the assertion.

Two further generic fixes, validating the world range of a generator's result and copying a plain generator's returned `CodeInfo` (bugs 3 and 2), are related but upstream-only and not part of this branch.

**Deliberate non-changes:** `may_invoke_generator`; `jl_type_infer` in `src/gf.c` (the sketch's step 7, see §7).

## 6. What crosses the boundary, and what does not

| Fact | `GeneratedFunctionTransform` | `OpaqueClosure` |
|---|---|---|
| Return type | inferred per concrete signature | declared `RetT`, enforced only opaquely |
| Effects | from `ipo_purity_bits` | `Effects()` (unknown) |
| Constant result | folded at codegen (`src/codegen.cpp:6325`) | call |
| Call | direct, known symbol | indirect through `specptr` |
| World range | on the world clock, capped by backedges | frozen |
| Caching | per specialization, shared by all call sites | per creation site |
| Callee-to-callee inside the transform | one inference domain | a boundary per closure |
| Stack frames | real: `error <- leaf <- target <- overdub <- caller` | none for the closure's origin |
| Package image | ordinary instance, serialized with its owner (fixes (e), (f)) | segfault (julia#55073) |

Deliberately still opaque: the transformed body is never inlined into native code, because it was produced under a different method table or lattice. Here that is a policy an owner could relax later (§8), not a soundness wall.

## 7. Departures from the original sketch

- **No `transform` field**: the constructor is `GeneratedFunctionTransform(gen)` (§3.2, Appendix D).
- **The call method is in Base**, routing to the interpreter's own `Compiler`; `Compiler` keeps only the implementation.
- **The invoke stub is the first implementer's choice**, not the sketch's; the sketch left the body's form open, and returning the transformed body directly is the main alternative (§8).
- The callable is `(g)(world, source::Method, args...)`, the real runtime protocol, not `(world, argtypes...)`.
- Failures throw instead of returning `nothing` (§4.4).
- Step 7, having `jl_type_infer` construct `owner(world)` in C, is not implemented; the runtime must not regenerate a tool's code behind its back, and `jl_invoke` already refuses to (`src/gf.c:4684`). The sketch's future-work idea, letting outer inference recognise this generator kind, is §8.
- Six supporting fixes (§5) were not anticipated.

## 8. Deep integration (future work)

The hook exists in outline. `Core.OptimizedGenerics.CompilerPlugins` (`base/optimized_generics.jl:59-81`, added with julia#56660) declares `typeinf(owner, mi, source_mode)` and `typeinf_edge(owner, mi, parent_frame, world, source_mode)`, dispatched on the owner and documented as licensing the optimizer to replace a `typeinf` call by `typeinf_edge` with the current inference stack and propagate the IPO-safe fields of the result. `Compiler/src` defines `typeinf(::Nothing, ...)` (`Compiler/src/bootstrap.jl:14`) but no pass consumes either function. `Compiler/extras/CompilerDevTools` implements both for its `SplitCacheOwner`, and its `with_new_compiler` (`CompilerDevTools.jl:67-77`: look up `mi`, `CompilerPlugins.typeinf(owner, mi, SOURCE_MODE_ABI)`, `invoke(f, ci, args...)`) is the run-time version of this feature.

Hook map (reasoned from the code, not implemented):

- Entry: in `Compiler.typeinf_edge` (`Compiler/src/typeinfer.jl:1293`), before `lookup_cached_edge`, when `method.generator isa GeneratedFunctionTransform`: build the inner interpreter and infer the looked-up callee as a child of `caller`.
- A new `CallInfo` lowered by the inliner to `:invoke foreign_ci`, since the caller still makes a foreign call unless the owner opts into native inlining.
- Cycles: `resolve_call_cycle!` (`:1071`) must see frames of both owners. `is_same_frame` (`:1056`) already compares `cache_owner`, but type-asserts the frame's interpreter to the caller's interpreter type, so a mixed frame graph would throw there before any owner comparison.
- The world question (§4.1) is unchanged: this path runs in `jl_typeinf_world`.

**Alternative: return the transformed `CodeInfo` as the body** (Nash's sketch). Probed with the inner interpreter's optimized `CodeInfo` returned directly (Appendix F):

| | invoke stub (this RFC) | direct body |
|---|---|---|
| Native visibility | rettype, effects, constant | whole body; native caller inlined it |
| Remaining foreign `:invoke` in inner IR | n/a | must be rewritten to `Core.invoke(f, ci, ...)`; left as is: "tried to double infer a function", then "Failed to invoke or compile external codeinst" |
| Body preparation | none | slot remap, `ssavaluetypes` reset |
| Cost per generation | one inner inference | inner inference plus native re-inference of optimized IR |
| Owner separation | kept | lost where inlined |
| Images, `--trim` | tested (images), hand-tested (`--trim`) | untested; the probe also dropped edges |

Questions for Nash:

1. Which world should interpreter code run in: the generated method's definition world, the requesting world, or `jl_typeinf_world`?
2. Is `CompilerPlugins.typeinf_edge` the intended hook, and should this be its first consumer?
3. May frames with different owners share a frame graph, and must cycle resolution compare owners?
4. Should the caller emit `:invoke` of the foreign instance, or may it inline IR the owner marks native-compatible?
5. Is optimized IR with `:invoke` rewritten to `Core.invoke` an acceptable generator return, or should there be an `isinferred`-style flag as for `OpaqueClosure`?
6. Is run-time `owner(world)` construction (the sketch's step 7) meant only for lazily compiling foreign instances?
7. Given the poisoning in §4.1, must `cache_owner` carry a version?
8. Is `Core._call_in_world_total` ignoring `in_pure_callback` intended?

Smaller points carried over from the previous revision: `abstract_invoke` returns the widened `rettype` even when the instance has `rettype_const` (inference could return `Const`); whether abstract callers (§4.3) may fall back to a declared type; the name; and the relation to `TypedCallable`/`InvokeLatestCallable` (julia#59774, julia#62245, julia#62559) and Keno's `await` draft (julia#58532), not yet compared.

Open items for the author, to settle before review:

- `Core.GeneratedFunctionTransform` is documented in the manual (`doc/src/base/base.md`) but is neither exported nor `public`, whereas `Core.GeneratedFunctionStub` is undocumented. Decide whether it is public API (and mark it `public`) or internal (and drop it from the manual).
- It is not a `Core.CachedGenerator`, so each native inference of the generated method in a new world reruns `gen` and the inner lookup (the inner `CodeInstance` itself is a cache hit). Whether it should be one, given that its result depends on the requesting world only through edges it already records.
- Fixes (c) and (e) treat the `:trim` owner differently: (c) drops `nothrow` for any `owner !== nothing`, including `:trim`, while (e) treats `:trim` as native. This is conservative, but a reviewer may ask to unify the two.

## 8b. A second use: runtime expressions without `eval`

Hash a runtime expression into a type tag, paste it in one ordinary generated method `evaluate(::Val{tag}, x)`, and reach it through the transform. On the branch build (2026-09-15) the world counter does not move, callers infer `Float64`, the generator runs once per (tag, argument types), and redefining a helper regenerates it. Relative to RuntimeGeneratedFunctions this adds the tool's interpreter, an ordinary call, and edges that survive a package image. The tag must be a content hash, because the registry lookup is a hidden edge.
